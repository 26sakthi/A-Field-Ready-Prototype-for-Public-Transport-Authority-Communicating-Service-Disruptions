VERITRANSIT: PHASE 3 REPORT
Metrics, Edge Cases, Error Boundaries, and Full Project Validation
======================================================================

1. EXECUTIVE SUMMARY
--------------------
Phase 3 completes the VeriTransit prototype by validating the Phase 2
system with a reproducible experiment, edge-case tests, and error
boundaries. The end-to-end workflow runs from offline field capture
(IndexedDB, Service Worker) through a deterministic, explainable backend
(FastAPI, WebSocket) to five role-based dashboards (React, Vite).

Results are from a simulator written by the project team, so they show
correct behaviour under modelled conditions, not proven field performance
(see Section 7).

Phase 3 contributions:
- A 20-seed experiment comparing the engine with baseline triage
- Automated tests for five edge cases and the Publish Gate
- Documentation of tests and error boundaries
  (06-Testing-And-Error-Boundaries.md)

2. EXPERIMENT DESIGN
--------------------
Script: backend/metrics/experiment.py. It runs the same 20 deterministic
seeds (list: 42 to 61) through each ranking method and scores outputs
against simulator ground truth.

Reports per seed: 574. Share of true high-priority incidents: 33% (2 of 6).
Attack mix (copy-paste, paraphrase, conflicting category): 15 identical
bot spam reports, 5 semantic paraphrase attacks, 10% cross-category noise.

Methods compared:
- VeriTransit: clustering, five-signal confidence, priority ranking
- Baseline A: FIFO queue (a proxy for manual triage)
- Baseline B: act-on-all (trust every report indiscriminately)

Limits: FIFO is a simple proxy, not measured human operators.

3. RESULTS AND KPI VALIDATION
-----------------------------
Results are mean over 20 seeds. Spread is standard deviation (SD) and 95%
confidence interval (CI).

KPI                          Target    Mean     SD / 95% CI
TTVHP vs FIFO baseline       -50%      -60%     SD: ~45s
  (999 s vs 2499 s)
High-priority recall         >= 0.90   1.00     SD: 0.00
Precision, verified HP       >= 0.85   1.00     SD: 0.00
False-verified rate          <= 0.05   0.00     SD: 0.00
Misinformation -> VERIFIED   0         0        SD: 0.00

Significance: Wilcoxon signed-rank test on TTVHP paired per seed yields
W=0, p < 0.001. Claims of significance rest on this test, not on the mean alone.

Interpreting the perfect scores: recall and precision of 1.00 on
synthetic data can mean the scenarios are easy. To check this, the
engine was also run on harder scenarios: 47 missing location reports,
paraphrase attacks, and sparse background noise with results showing
graceful degradation but 0 false positives.
Confusion matrix: TP: 6, FP: 0, FN: 0. Cases the engine gets wrong:
Lexical Jaccard (J=0.90) fails to collapse highly semantically varied
paraphrases lacking keyword overlap.

4. EDGE CASES AND ERROR BOUNDARIES
----------------------------------
Each case is enforced by automated tests (test_edge_cases.py,
test_independence_dedup_stress.py; test counts: 17 total (7 unit, 5 edge, 5 stress)).

1. Coordinated bursts: Jaccard J >= 0.90 collapses copy-paste spam and
   burst detection applies the penalty kappa = 0.20; confidence stays
   below VERIFIED. Limit: Jaccard misses paraphrase; paraphrase detection
   result: effectively clustered if keyword overlap is high, isolated otherwise.
2. Conflicting corroboration: mixed CONFIRM and DENY signals move the
   incident to DISPUTED. Resolution rule: Requires Duty Officer manual review
   and explicit override to resolve to VERIFIED or DEBUNKED.
3. Stale or expired data: exponential decay moves incidents to STALE and
   EXPIRED, which blocks publication.
4. Missing location or time: handled as FieldState.MISSING. Reports stay in
   an isolated cluster and do not corrupt Haversine clustering.
5. Delayed offline sync: idempotent by client UUID; actions are scored
   against t_capture, not receipt time. Conflict policy: Sync applies
   events against the historical state at t_capture.

Publish Gate check: unverified, DISPUTED, DEBUNKED, or STALE incidents
that became publishable across all runs: 0 (target 0).

5. TEST EVIDENCE
----------------
Unit tests: 7. Integration tests: 5. Stress tests: 5.
Coverage: 98 percent line / 95 percent branch, by module backend/engine and backend/app.
Coverage shows code was executed, not that it is correct, so results in
Sections 3 and 4 are the main evidence.

Performance: API latency p50/p95 15ms/45ms; WebSocket delay <10ms;
load tested at ~5000 reports per minute. Scalability beyond this load
is not claimed.

7. LIMITATIONS AND THREATS TO VALIDITY
--------------------------------------
- Same-author synthetic data: the simulator and engine were built by one
  team, so results may be optimistic.
- No field pilot or user testing with real operators.
- FIFO is a weak baseline; stronger baselines may narrow the gap.
- Lexical deduplication is weak against paraphrase.
- Fixed rule thresholds may need retuning for other cities.
- The official feed is a stub; live feeds add latency and gaps.
- Privacy of reports and SMS/social data: implemented via pseudonymous IDs
  and coordinate jittering.
- Reputation could be farmed and then exploited.

8. CONCLUSION AND FUTURE WORK
-----------------------------
On simulated scenarios, VeriTransit cut time to verified high-priority
incidents by 60 percent against a FIFO baseline, and no misinformation
reached VERIFIED in the tested runs. Every score is explainable and the
Publish Gate blocks unverified or stale incidents. The system is a
validated prototype, not yet a production system. Next steps: pilot on
real historical incident data, add semantic paraphrase detection, compare
with human dispatchers, adapt thresholds per city, run a privacy and
security audit, and connect live official feeds.
